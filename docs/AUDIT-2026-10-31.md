# Аудит аккаунтов и равномерности фарма, 31 октября 2026

Проверены запуск Windows, импорт account.txt, Android/device-code и Kick-вход,
удаление аккаунтов, SQLite, пул работников, цикл просмотра Twitch, обработка
инвентаря, сетевые адреса плейлистов и маяков, очередь групп и интерфейс аккаунтов.
Исправления внесены в исходники и журнал изменений. Версия не выпускалась.

## Найденные причины и исправления

| Проблема | Причина | Исправление |
| --- | --- | --- |
| Медленный импорт | UI ожидал завершения каждого запроса; поиск существующего пользователя заново расшифровывал все сохранённые сессии | Один пакетный запрос, до 16 одновременных проверок, один индекс пользователей на пакет; операции записи защищены от создания дублей |
| Медленное удаление всех аккаунтов | Отдельные HTTP-запросы и транзакции для каждого аккаунта; остановка происходила после удаления данных | Один DELETE-запрос и одна транзакция с массовыми SQL-операциями; работники заранее остановлены |
| Конфликты с майнерами | Импорт и удаление выполнялись одновременно с просмотром | Общая блокировка операций аккаунтов и пауза пула; ожидание завершения всех работников; перезапуски откладываются до завершения операции |
| Временные провалы фарма | Ошибка чтения инвентаря уничтожала успешный просмотр и запускала повторный выбор канала | Просмотр сохраняется, чтение повторяется в следующем цикле |
| Задержка минутного сигнала | Последовательное выполнение HLS-проверок и Spade-маяка; сетевые повторы складывали задержки | Два независимых пути запускаются одновременно, общий бюджет операции просмотра 25 секунд; основной интервал остаётся 60 секунд |
| Обход проверки сетевого адреса | Проверялся исходный адрес, но HTTP-клиент автоматически следовал перенаправлениям | Проверяется каждый адрес перенаправления для HLS, маяков, страницы канала и settings.js; адреса с OAuth в production требуют HTTPS |
| Неполная очистка | Явный purge покрывал не все дочерние таблицы; отсутствовал Release при остановке пула | Добавлены зависимые строки, ключи authcheck/skip/link, освобождение регистраций и очистка кэша предупреждений удалённого аккаунта |
| Недетерминированный порядок групп при параллельном импорте | Ответы сети приходят в произвольном порядке | Назначения групп записываются одним обновлением в исходном порядке файла |

Массовая очистка сохраняет исторические таблицы `claim_log` и `watch_minutes`,
как и прежнее одиночное удаление. Настройки приложения, администратор и история
полученных наград не сбрасываются. Это не удаление файла базы и не VACUUM;
размер SQLite на диске может остаться прежним, освобождённые страницы переиспользуются.

Не гарантируется мгновенная остановка уже выполняющегося сетевого запроса:
операция ждёт отмены и корректного завершения работников и sidecar-просмотра.
Зато запись/очистка не начинается до завершения майнеров. Ошибка SQL откатывает
массовую очистку. Импорт допускает частичный успех и возвращает результат каждой
строки; отмена запроса не откатывает аккаунты, уже успешно сохранённые ранее.

## Почему 100 аккаунтов могут иметь разный прогресс

1. Разные группы из account.txt работают **по очереди**. Одновременный фарм всех
   аккаунтов требует одной группы либо аккаунтов без разделения на группы.
2. Настройка волн по 20 аккаунтов добавляет паузу в одну секунду между волнами.
   Для 100 аккаунтов это около четырёх секунд плюс стоимость подготовки аккаунтов.
   Сама эта настройка не объясняет отставание на 10–20 минут.
3. Ошибки инвентаря раньше приводили к остановке просмотра. Это исправлено.
4. Медленный HLS раньше задерживал независимый маяк. Это исправлено. Остальные
   сетевые операции, включая обновление каталога кампаний, всё ещё выполняются
   в цикле аккаунта и при большой задержке могут растянуть его более чем на минуту.
   Добавлен журнал `runner tick exceeded heartbeat interval` с идентификатором
   аккаунта и длительностью. Полного отделения сканирования от цикла просмотра
   в этой правке нет.
5. Ответы платформы, ограничения сети/IP, разные каналы, смена трансляции,
   завершение наград и задержка обновления инвентаря также могут давать разброс.
   Локальный таймер или успешный HTTP-ответ не доказывает начисление минуты платформой.

В локальной `data-test/miner.db` при проверке было 20 включённых Twitch-аккаунтов
и 20 записей сканирования без сохранённой ошибки. Сценарий со 100 аккаунтами
на активном дропе не воспроизводился. Локальная база и ключ не изменялись.

Для живой проверки следует сравнить прирост одного и того же дропа за 30–60 минут
по всем участникам одной активной группы, включая аккаунты с нулевым приростом.
Сопоставлять нужно также время фактического старта, ошибки heartbeat/inventory,
смены каналов и предупреждения о долгом цикле. Только после этого можно судить,
насколько уменьшился разброс и остались ли ограничения со стороны платформы.

## Проверки

- `go build ./...`: успешно.
- `go test ./...`: 928 тестов, без ошибок; 29 пакетов с успешными тестами.
- `npm --prefix web test`: 378 тестов в 28 файлах, без ошибок.
- `npm --prefix web run check`: 0 ошибок, 0 предупреждений.
- `npm --prefix web run build`: успешно, SPA собрана в `internal/web/dist`.
- `gofmt -l cmd internal`: список пуст.

Новые регрессионные проверки покрывают параллельный вход, дубли пользователя,
паузу/отложенный перезапуск пула, транзакционный откат удаления, дочерние строки,
сохранение просмотра при ошибке инвентаря, порядок групп, блокировку перенаправлений
и независимость маяка от медленного плейлиста.

Исправлена переносимость существующих тестов на Windows: модельные тики не
зависят от наносекундного разрешения часов; POSIX-биты прав не проверяются на
Windows, MIME JavaScript допускает оба варианта ОС.

Race detector не запускался: в окружении `CGO_ENABLED=0`, GCC не найден.
Docker-образ, Kick transport canary, живое начисление Twitch/Kick и получение
наград не проверялись. Это аудит перечисленных путей, а не доказательство
отсутствия всех уязвимостей или утечек во всём проекте. Проверка зависимостей
по актуальной базе CVE также не выполнялась.

## Запуск

Для запуска используется только `run-miner.bat`.
Лаунчер пересобирает SPA и `grubdrops.exe`, затем открывает существующую базу
`data-test/miner.db`. Для применения изменений нужно перезапустить программу
через этот файл. Уже запущенный старый процесс автоматически не обновляется.

Изменения пути начисления оставлены в `[Unreleased]`: по правилам проекта тег
возможен только после подтверждения начисления на активном дропе.
